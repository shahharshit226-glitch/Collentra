# Collentra — Row Level Security Reference

Full runnable form: `supabase/migrations/0012_rls_policies.sql`. This doc
explains *why* each policy is shaped the way it is, and lists the security
tests (spec §95/§96) it should pass.

## Ground rules

- **Default-deny.** Every table has `ENABLE ROW LEVEL SECURITY` and only
  the operations listed below are possible for the `authenticated` role.
  A table with no `INSERT` policy simply cannot be inserted into by a
  client — that's intentional for `project_members`, `conversations`,
  and `notifications`, all of which are written only by trigger functions.
- **`SECURITY DEFINER` is used sparingly and deliberately** — only for
  functions that legitimately need to read/write across users (the
  matching engine, `get_contact_email`, and the workflow triggers in
  `0011_workflow_triggers.sql`). Every other function runs as the calling
  user and is fully subject to RLS.
- **Never trust the frontend for admin checks** (§65). `is_admin(uid)` is
  a `SECURITY DEFINER` SQL function reading `admin_users`; it's the only
  thing any policy or the admin dashboard uses to gate admin actions.

## Table-by-table reasoning

| Table | Read | Write | Why |
|---|---|---|---|
| `profiles` | `can_view_profile()`: self, admin, or (target verified AND not blocked either direction) | self or admin can `UPDATE`; `account_status` self-changes blocked by a separate trigger | A suspended/blocked student's `account_status` must not be self-editable — RLS `USING`/`CHECK` can't compare old vs new column values, so this is a trigger, not a policy. |
| `profile_private` | owner or admin | owner (phone/roll number) | This is *the* column-privacy mechanism — see `ARCHITECTURE.md` §3. |
| `availability` | same visibility as the profile | owner only | Read visibility mirrors `profiles` via the shared `can_view_profile()` helper so the two never drift apart. |
| `skills`/`interests`/`roles` + aliases | everyone (active rows) | admin only | Reference data (§61/§62): students choose from it, only admins curate it. |
| `student_skills`/`student_interests`/`student_preferred_roles` | profile-visibility rule | owner only | A student's chosen skills are exactly as visible as the rest of their profile. |
| `projects` | everyone, except from a creator who has blocked/been blocked by the viewer | creator (or admin) | Public discovery (§20) is the point; blocking still has to hide it (§56). |
| `project_required_*` / `project_interests` | everyone | project creator only | Requirements are shown on every project card; only the owner edits them. |
| `project_members` | everyone (team roster is shown on project detail, §52) | `UPDATE`/`DELETE` by the member themself (leaving) or the project creator (removing); **no `INSERT` policy** | Joining a project must go through the application flow, not a direct write — otherwise anyone could add themselves to any team. |
| `project_applications` | applicant, project creator, or admin | `INSERT` by the applicant (must be verified, not already a member); `UPDATE` (accept/reject) by the creator only | The creator makes the final call per §22 — a student cannot self-accept. |
| `connections` | either party or admin | `INSERT` by the requester (blocked pairs rejected); `UPDATE` (accept/reject) by the addressee only | Mirrors the same "decision belongs to the other party" pattern as applications. |
| `blocked_users` | the blocker or admin | insert/delete by the blocker only | A block is unilateral and private to the blocker. |
| `reports` | the reporter or admin | `INSERT` by the reporter; `UPDATE` (status) admin only | Reports must be triage-able by admins without being visible to the reported user. |
| `discovery_skips` | owner only | owner only | Purely a per-user "don't show me again for a while" list. |
| `conversations` | any current member, or admin | none for clients — created only by trigger | Prevents joining an arbitrary conversation by guessing/inserting an id. |
| `conversation_members` | any fellow member, or admin | `UPDATE` (own `last_read_at`) only | Membership changes flow from project/connection triggers, not direct writes. |
| `messages` | any member of that conversation | `INSERT` by a current member, `sender_id` must be self | Straightforward membership check; no `UPDATE`/`DELETE` policy in v1 (no edit/delete-message feature yet). |
| `notifications` | the recipient only | `UPDATE` (mark read) by the recipient only; **no client `INSERT`** | All notifications are system-generated by `SECURITY DEFINER` triggers. |
| `project_feedback` | either party in the feedback, or admin | `INSERT` by a current/former project member about another member | Kept private per §87 — not publicly visible, not read by matching. |
| `admin_users` | self or admin | none for clients | Admin grants happen out-of-band (dashboard/service role), never via the app. |
| `matching_settings` | admin only | admin only, with the sum-to-100 check re-validated | Weights are an internal tuning knob (§34 says don't even show the score to normal users), so no reason for student-role read access; the matching functions themselves read it as `SECURITY DEFINER` regardless. |

## Security test checklist (spec §95/§96)

Run these against a real Supabase project (RLS behaves differently under
the `service_role` key vs an authenticated user's JWT — always test as an
authenticated non-admin user):

1. A user cannot `SELECT` another user's `profile_private` row.
2. A user cannot `UPDATE` their own `account_status`.
3. A suspended/blocked user's mutating requests (connection request,
   application, project creation, message) all fail — verify each
   directly, don't assume `account_status` alone blocks writes; the
   relevant policies should additionally check `account_status = 'verified'`
   where the spec requires it (currently: `projects_insert`,
   `project_applications_insert`; extend to `connections_insert` and
   `messages_insert` if you want suspended users fully muted rather than
   just blocked from *new* projects/applications — decide and encode it,
   don't leave it implicit).
4. A blocked user disappears from `fn_recommended_partners`,
   `fn_projects_needing_skills`, and `fn_discover_candidate` output, and
   from `profiles_select`/`projects_select` in both directions.
5. A non-member cannot `SELECT` from `messages` or `conversation_members`
   for a conversation they're not in, even by guessing a UUID.
6. A student cannot `INSERT` directly into `project_members` or
   `conversations` — only the accept-application / accept-connection
   flows can create those rows.
7. A non-admin gets zero rows from `admin_users` (other than their own,
   which won't exist) and cannot `UPDATE` `matching_settings`.
8. `matching_settings` rejects an update where the six weights don't sum
   to exactly 100.
9. Roll number and phone number never appear in any query result to a
   non-owner, non-admin — including indirectly via a join (test with a
   `select * from profiles join profile_private ...` as a non-owner and
   confirm RLS still blocks the `profile_private` side).

## Note on `SECURITY DEFINER` functions

Every `SECURITY DEFINER` function in this schema explicitly checks the
caller's eligibility *inside the function body* before doing anything
sensitive (e.g. `get_contact_email` checks for an accepted, non-blocked
connection before returning an email address). `SECURITY DEFINER` bypasses
RLS for that function's own queries — it does **not** bypass the
eligibility logic you write inside it. Review any new `SECURITY DEFINER`
function added later with that in mind before merging it.

## Connection acceptance into project teams

Migration `0016_accept_connection_to_project.sql` exposes `accept_connection_to_project()` to authenticated users. The security-definer function checks the caller against the request addressee and project creator, validates pending status and available capacity, then changes the connection status and inserts the project membership in one transaction. The existing triggers create chat membership and maintain the project count. Clients cannot insert project membership or conversations directly.
